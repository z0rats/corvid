# Corvid — project context

Self-hostable, single-user OSINT/security-analyst web app. FastAPI backend + React frontend, runs via Docker Compose. Not production-hardened (early prototype, per README).

**Maintenance:** this file loads in full on every message regardless of task, so its size is a standing tax on every conversation — treat growth as a cost, not a free action.

- Update it after any important project change (new feature, new external dependency, architectural shift) — but each edit is a *net* pass: prune or tighten something (merge, generalize, cut what's now covered elsewhere or obvious from the code) roughly as much as you add. Don't just append.
- Record big architectural decisions (new dependency choice, schema/storage tradeoffs, anything picking one approach over a real alternative) as a new `docs/adr/NNNN-*.md` — don't let the reasoning live only in chat/commit history. Keep entries in this file itself pointer-short; the ADR holds the "why".
- Describe the **current state only**. No "was X, changed to Y because Z", no "see commit/PR #123", no incident narratives, no migration history — that belongs in commit messages and git history, which are queryable on demand and don't cost tokens on every turn. If a past decision needs to stay discoverable, a short present-tense reason clause (e.g. "X, since Y" ) is fine; a paragraph of backstory is not.
- No speculative or redundant detail.
- If this file is pushing 25KB+, that's a signal to condense before adding more — collapse verbose bullets, drop detail that's redundant with the code itself, and prefer pointing at a file/symbol over re-explaining what it does.
- Also periodically update `README.md` with important user-facing changes — especially anything affecting deployment (new required setup step, changed env vars, new `.env`/`docker-compose.yaml` behavior) — since that's what operators actually read when installing/upgrading.

## Git

Never run `git commit` (or `git push`) yourself, create new tags or releases, regardless of how the rest of the task is scoped or how routine the change looks. Stage or leave changes uncommitted and let the user review and commit. This holds even if a broader instruction ("go ahead and update the repo", "ship this") could be read as covering it.

## Stack

- **Backend**: Python 3.14, FastAPI, SQLAlchemy 2.0 (async, `aiosqlite`/`asyncpg`), Alembic migrations, APScheduler for background jobs, `pydantic-ai-slim[anthropic,google,openai]` for LLM features (the bare `pydantic-ai` metapackage is deliberately not installed — it hard-depends on every provider SDK; `app/utils/llm_service.py`'s model registry also auto-discovers models pulled into a local Ollama server via its OpenAI-compatible `/v1/models` endpoint - `LLM_OLLAMA_BASE_URL`, no API key needed, silently skipped if unreachable), `slowapi` for rate limiting, pytest for tests.
- **Frontend**: React 19, MUI 9, Jotai (state), react-router 8 (declarative mode only - `BrowserRouter`/`Route`/hooks imported from `react-router`, not the removed `react-router-dom` package), Vite (build/dev server) + Vitest (tests, jsdom), ESLint 9 flat config (`frontend/eslint.config.mjs`), Yarn 4 (berry, `packageManager: yarn@4.15.0`).
- **DB**: SQLite by default at `data/corvid.db` (see `backend/app/core/config/settings.py` — `DatabaseSettings`, env prefix `DB_`). Logs at `data/logs/`.
- **Deploy**: `docker-compose.yaml` — `backend` (no exposed port, mounts `./data`) + `frontend` (nginx, port 4000). `make up` / `make rebuild` / `make up-backend` / `make up-frontend` (see `Makefile`). Backend runs as non-root `appuser` (UID/GID 1000): `backend/docker-entrypoint.py` starts as root just long enough to `chown` the host-owned bind-mounted `./data`, then drops to `appuser` via `setuid`/`setgid`, runs migrations (see below), and `execvp`s into the real `uvicorn` command. `appuser`'s home directory (build-time, not bind-mounted) is where maigret's site-database (`~/.maigret`) and pyppeteer's lazily-downloaded Chromium (`~/.local/share/pyppeteer`, only if `email_search`'s headless checks are enabled) end up.

## Backend architecture

Entry point: `backend/main.py` — builds the FastAPI app via `create_fastapi_application()`, lifespan hooks create DB tables, run app defaults, start background favicon fetch, start scheduler.

Layout under `backend/app/`:
- `core/` — cross-cutting: `config/` (settings, CORS, security headers, rate limiting, request-id, body-limit middleware), `settings/` (persisted app settings: `api_keys` — `Apikey.key` is encrypted at rest via `EncryptedString`/`secrets_crypto.py` (Fernet; key from `SECURITY_ENCRYPTION_KEY` or auto-generated at `<data_dir>/.encryption_key`, 0600 — back that file up with the DB, or losing it makes stored keys unrecoverable; legacy plaintext rows still read fine and get encrypted on next save) plus a live quota panel (`routers/quota_routes.py`'s `GET /api/services/quota`, hitting VirusTotal/Shodan/Hunter.io's own quota endpoints with the stored key — the only three wired providers with one), `ai_settings`, `general`, `keywords`, `modules`, `cti_profile` — each has its own models/schemas/crud/routers under `core/settings/<name>/`), `security/ssrf_guard.py` (resolves + validates the hostname of any user-supplied URL before it's fetched server-side, rejecting private/loopback/link-local/reserved IPs; `safe_get(client, url, ...)` is the single shared entrypoint — pins the resolved IP for the request *and* manually re-validates each redirect hop, since httpx's own `follow_redirects` would re-resolve `Location` without going through this check; callers must construct their `httpx.AsyncClient` with `follow_redirects=False`. Covers every feature that fetches a user-supplied or externally-sourced URL over `httpx` (favicon downloads, newsfeed article/feed fetching, LLM-template web content, domain WHOIS/RDAP redirects); opt-out via `SECURITY_ALLOW_PRIVATE_NETWORK_TARGETS`, dev/testing only. `git_recon`'s repo-clone target is the one outbound-fetch path *not* on `httpx` — see its own feature bullet below for the subprocess-argv allowlist that plays the same role there), `reports/` (generic HTML/PDF report renderer — `render_html`/`render_pdf` via Jinja2 + `xhtml2pdf`, `generate_report(title, sections, fmt, locale, ...)`; feature-level `report_service.py` modules build `ReportSection`/`ReportRow` lists with their own small `en`/`ru` label dicts and call into this; used by `ioc_lookup` single-lookup history (`GET /api/ioc-lookup/history/{id}/report`) and `email_analyzer` (`POST /api/email/report`, stateless — takes the analysis result in the body since there's no persisted history to fetch by ID), `alerts/` (WebSocket alerts), `database.py`, `scheduler.py`, `dependencies.py` (includes `get_disk_space_health` — warns at `"low"` below `AppSettings.low_disk_space_threshold_bytes` (env `LOW_DISK_SPACE_THRESHOLD_BYTES`, default 1 GiB) free on `data_dir`; logged once at startup via `main.py`'s `_check_disk_space` and re-checked on every `/api/healthcheck/detailed` call), `exceptions.py`, `healthcheck.py` (basic/detailed/`ready`/`live` probes; detailed status is `"degraded"`, not `"unhealthy"`, when only disk is low).
- `features/` — one directory per product feature, each typically split into `routers/`, `service/`, `schemas/`, `models/`, `crud/`, `utils/`, `config/`:
  - `newsfeed/` — RSS aggregation, IOC extraction from articles, MITRE ATT&CK mapping, trends/analytics. Each `NewsfeedSettings` row tracks `last_fetched_at`/`last_success_at`/`last_error`, updated per-feed by `feed_processing_service.py`'s `process_feed_chunk` on every scheduler run, so a persistently failing feed (bad URL, provider outage) shows a warning in the feed management UI instead of only ever appearing in logs.
  - `ioc_tools/` — `ioc_lookup` (single + bulk lookups against AbuseIPDB, AlienVault, VirusTotal, Shodan, etc.; single-lookup searches are auto-saved to history once every queried service responds, via `POST/GET/DELETE /api/ioc-lookup/history`, persisted as `SingleLookupSearch`/`SingleLookupResult`; `GET /api/ioc/newsfeed-mentions` cross-references a looked-up IOC against `newsfeed`'s already-extracted article IOCs — `newsfeed_crud.get_articles_mentioning_ioc` matches by raw value via a case-insensitive JSON-text `LIKE` against `NewsArticle.iocs` rather than by type, since the two features' IOC-type vocabularies don't line up), `ioc_extractor`, `ioc_defanger`, `domain_finder` (URLScan.io-based typosquat/phishing domain discovery, `/api/domain/lookup`; sibling panels on the same page: WHOIS/RDAP via `rdap.org`'s bootstrap redirector, DNS records via dnspython plus reverse-DNS for resolved IPs, and Certificate Transparency subdomain enumeration via crt.sh's public JSON mirror — all three keyless. A fourth, DNSDumpster (`/api/domain/dnsdumpster`), enriches with ASN/geo/PTR/HTTP(S) banner data per host but needs its own free-tier API key from `dnsdumpster.com`, configured under Settings > API Keys like any other provider — capped at 50 records/lookup, no domain-map image or pagination (Plus-tier only, not integrated)).
  - `email_analyzer/` — `.eml` parsing, header/IOC checks, AI-assisted analysis.
  - `image_tools/` — EXIF/metadata extraction, hashing, reverse image search deep-links (no API key needed), plus an optional AI photo-geolocation hypothesis (`POST /api/image/geolocate`, `image_geolocation_service.py`) reusing `llm_service.py`'s multimodal support (`execute_structured_prompt`'s `image_data`/`image_media_type`) — the module's only feature needing an LLM key or an `ai_settings.image_geolocation_model` override; still fully stateless like the rest of the feature (no history persisted). See `docs/geoint-photo-analysis-plan.md` for the fuller backlog this MVP slice came from.
  - `llm_templates/` — user-defined AI prompt templates (categories + templates).
  - `cvss_calculator/` — CVSS 3.1/4.0 scoring.
  - `username_search/` — two pluggable sources behind one unified schema (`MaigretSearch`/`MaigretSiteResult`, with a `source` column: `maigret` | `social_analyzer`, and a `extra` JSON column for source-specific display data), selected per-scan via `ScanRequest.source` (`POST /api/username-search/scan`):
    - **maigret** — called in-process (not subprocess) via `maigret.checking.maigret()`, true per-site progress streamed over SSE; settings under `core/settings/username_search/` (timeout/concurrency/top-sites-count/proxy, site-database auto-update tracking, plus a manual PyPI-latest-version check for the `maigret` package itself — same pattern as social-analyzer below, `POST /api/username-search/maigret/check-update`).
    - **social-analyzer** — invoked as a **subprocess** of its installed CLI (`social_analyzer_service.py`, `--output json`), *not* in-process: the installed package's on-disk module directory is named with a hyphen (not a valid Python identifier), so it can't be imported — only `importlib.metadata` (version/site-count) and the console script are usable. No per-site progress callback exists either, so the SSE stream is coarse (`started` → one terminal event); cancellation kills the subprocess, and a `PROCESS_WATCHDOG_SECONDS` (30 min, `social_analyzer_config.py`) wall-clock ceiling force-kills it even with no client watching, since `timeout_seconds`/`top_sites_count` can both be user-configured to 0 (unbounded). Settings/version-check under `core/settings/username_search/social_analyzer_settings_*` (timeout/top-sites-count, plus a manual PyPI-latest-version check, `POST /api/username-search/social-analyzer/check-update`). For both tools this only flags an available update (`UsernameSearchInfo.update_available`) — installing it still requires a container rebuild, since packages are pinned in `requirements.txt` at image-build time, not runtime-installable by the non-root container user.
    - Report export (`report_service.py`) reuses Maigret's own report writers and only works for maigret-sourced runs; social-analyzer runs just report `has_export: false`.
    - A keyless, ephemeral supplementary check (`GET /api/username-search/hudson-rock`, `hudson_rock_service.py`) queries Hudson Rock's free infostealer/malware-log-exposure API per username and renders as a compact clean/found status chip above the found-sites list — not persisted, not a `ScanRequest.source`, same pattern as `ioc_lookup`'s newsfeed-mentions cross-reference.
  - `email_search/` — finds which mail providers a username is registered at, via `mailcat-osint`'s ~26 per-provider checker coroutines (SMTP RCPT probing, provider APIs, registration-form probing, headless Chromium). Driven in-process (no reusable entrypoint exists in mailcat like maigret's, so `service/email_search_service.py` runs the checker coroutines itself, bounded by an `asyncio.Semaphore`), progress streamed over SSE (`POST /api/email-search/scan`), found-provider results persisted (`MailSearch`/`MailSearchResult`). Two checker groups are gated off by default via settings (`core/settings/email_search/`, `enable_smtp_checks`/`enable_headless_checks`): SMTP checkers (Gmail/Yandex/mail.de) need outbound TCP/25 usually blocked in Docker/cloud (workaround: `use_tor`/`proxy_url`, mirroring mailcat's own `--tor`/`--proxy`); headless-Chromium checkers (Fastmail/int.pl/onet.pl, via `requests-html`→`pyppeteer`) lazily download a Chromium binary on first real use. Each checker call is wrapped in a hard per-checker `asyncio.wait_for` timeout; mailcat itself closes its browser handle in a `finally` that survives cancellation, but as a safety net for a wedged Chromium process that never responds to `browser.close()`, `_kill_orphaned_chromium` (psutil-based, diffs child PIDs before/after) reaps any Chromium process still alive after a timeout. Like social-analyzer, version/update-check is a manual PyPI-latest check (`GET /api/email-search/info`, `POST /api/email-search/check-update`), latest-available version persisted on `EmailSearchConfig`.
  - `reddit_search/` — finds a Reddit user's full post/comment history, including moderator-removed and author-deleted content, by querying the public Arctic Shift (`arctic-shift.photon-reddit.com`) and PullPush (`api.pullpush.io`) archive APIs in parallel (no auth/API key; server-side port of the frontend-only [Rosint](https://github.com/zuxu4n/Rosint)). `service/reddit_search_service.py` merges+dedupes results by Reddit item ID and sorts desc by `created_utc`; pagination is timestamp-cursor-based (`before`/`after` on `created_utc`), not offset-based. One `RedditSearch` row persists per username investigation (`POST /api/reddit-search/scan`, called once per page per posts/comments tab), with pages appended idempotently to `RedditSearchResult` (unique on `search_id`+`kind`+`reddit_id`) so re-fetching a page while paging back doesn't duplicate rows. No settings module — no tunables, nothing to configure.
  - `dork_runner/` — runs a static library of parameterized dork templates (`site:`, `filetype:`, `intext:`, etc., `config/dork_templates.py`) against a domain/username/email, ephemeral like `domain_finder` (no persistence/history). DuckDuckGo's HTML endpoint is the default engine since Google/Bing block scripted queries almost immediately; Google/Bing are still selectable but best-effort. Queries run sequentially with a politeness delay between them (`config/search_engines_config.py`), never in parallel. `POST /api/dork-runner/run`, `GET /api/dork-runner/templates`.
  - `youtube/` — metadata lookup for a YouTube video URL (`POST /api/youtube/lookup`), ephemeral like `domain_finder`/`dork_runner` (no persistence). Keyless tier: oEmbed (title/author/thumbnail/embed html) plus a best-effort scrape of the video page's Open Graph/schema.org `<meta>`/`<link>` tags (`youtube_page_service.py`) for description/duration/publish-date/keywords oEmbed doesn't expose, plus directly-constructed `i.ytimg.com` thumbnail URLs at every standard resolution (no fetch needed, may 404 for `maxresdefault`). An optional YouTube Data API v3 key (`core/settings/api_keys`, service key `youtube`) unlocks view/like/comment counts, tags, and category — same optional-key pattern as DNSDumpster. That key is mandatory (not optional) for the sibling `POST /api/youtube/comments` endpoint, since comments have no keyless tier at all: with no `query` it's a plain single-page listing (`page_token` pagination); with a `query` it scans multiple pages server-side filtering by author/text substring, since the Data API has no native comment-text search — capped on both pages and result count (`youtube_config.py`), returning `truncated: true` plus a `next_page_token` to keep scanning if the cap was hit before the video's comments were exhausted. `youtube_url_utils.extract_video_id` handles `youtu.be`/`watch`/`shorts`/`embed`/`live` URL shapes.
  - `git_recon/` — wraps [gitcolombo](https://github.com/Soxoj/gitcolombo) (stdlib-only, imported in-process — `service/git_recon_service.py` drives its `GitAnalyst` directly rather than calling its CLI `main()`, so results come back as structured objects instead of parsed ANSI text) to correlate names/emails/GitHub logins from commit history. Three modes (`ScanRequest.mode`): `search` is API-only (GitHub `/gpg_keys` + `/search/commits`, no cloning); `url`/`nickname` clone one repo or every public non-fork repo of a user/org and correlate author/committer identity mismatches across `git log --all`. `POST /api/git-recon/scan` streams progress over SSE (background `asyncio.create_task` + queue, same shape as `username_search`/`email_search` below, `started`/`completed`/`cancelled`/`failed` only — gitcolombo has no per-item progress callback) rather than blocking the request for the scan's full duration, which can run up to `WALL_CLOCK_TIMEOUT_SECONDS` (nginx's `/api/` `proxy_read_timeout` is raised to match, or it'd 504 the client mid-scan while the backend kept running regardless). Cancellable via `POST /api/git-recon/history/{id}/cancel` and `core/scans/cancellable.py`'s `GitCloneCancellable`, which reaps the scan's own git subprocesses (psutil, same before/after-pid-diff pattern as `email_search`'s Chromium reaper below) rather than cancelling the asyncio task directly, since the clone/log calls run inside a worker thread (`asyncio.to_thread`) with no cancellation point of its own. gitcolombo's `git clone` is a `subprocess` call that (unlike every other outbound fetch in this codebase) isn't `httpx`, so it's outside `ssrf_guard`'s reach — `validate_github_repo_url`/`validate_github_nickname` in the service module are the sole gate restricting any user-supplied target to `https://github.com/<owner>/<repo>` before it reaches subprocess argv (regression-tested in `tests/features/git_recon/test_url_allowlist.py`, since the repo-wide `test_ssrf_guard_coverage.py` only scans for raw `httpx`/`requests` clients). Clones into an ephemeral `tempfile.mkdtemp()` dir, `rmtree`'d in a `finally`; `config/git_recon_config.py` caps repo count/clone workers/wall-clock time per scan (full, non-shallow clones needed for `--all` history). Reuses the `github_pat` row from `core/settings/api_keys` rather than a separate credential — `nickname` mode's repo-discovery step (`_get_public_repos_count`/`_get_github_repos`) sends it as a Bearer header itself, since gitcolombo's own equivalents don't accept a token at all (only its gpg_keys/search-commits calls, used by `search` mode, do) and would otherwise silently fall back to GitHub's unauthenticated 60/hour cap regardless of a configured PAT. In `url`/`nickname` mode each identity also carries a `mentions` list (per-repo commit counts + one sample commit SHA, clickable through to `<repo_url>/commit/<sha>`) — reconstructed in `_run_clone_mode_sync` by slicing `analyst.commits` per repo right after each `analyst.append()` call, since gitcolombo's own `Person` only retains a single last-seen repo/commit, not full provenance. A `GitReconSearch` row is created in `running` state before the scan starts, updated to `completed`/`cancelled`/`failed` after (interrupted-by-restart rows reconciled to `failed` by `main.py`'s `_reconcile_stale_scans`, like the other two SSE-scan features); result stored as a JSON blob (graph-shaped output — not worth normalizing into FK tables for the only consumer).
- **Access control**: the app has no user accounts (single-user tool) — instead, `core/security/access_control.py` guards every `/api/*` route (plus `/docs`/`/redoc`/`/openapi.json`, added back in `main.py` after `fastapi_config.py` disables FastAPI's built-in ones) behind one shared bearer token, checked via `verify_access_token` wired as a router-level dependency in `router_registry.py`. Token comes from `API_ACCESS_TOKEN` or is auto-generated and persisted to `<data_dir>/.access_token` (0600) on first startup, printed once to stdout/logs — same pattern as the encryption key, factored into `core/security/persisted_secret.py` and shared by both. `healthcheck.router` and the alerts `ws_router` are the only routers registered without this dependency: healthcheck has no sensitive data, and the WebSocket handshake checks the same token itself via a `?token=` query param (browsers can't set a custom header on a WS handshake) — see `alerts_routes.py`. Frontend: `core/services/baseApi.js` attaches the token from `localStorage` (`core/utils/accessToken.js`) to every request and reloads the page on a 401 from an already-set token; `core/components/ui/AccessGate.jsx` shows a one-time entry screen when no token is stored yet, wrapping `AppRoutes` in `App.jsx`.
- All routers are aggregated in `backend/app/utils/router_registry.py` via `get_core_routers()`, `get_settings_routers()`, `get_feature_routers()`, then mounted in `main.py`.
- Migrations: Alembic, config at `backend/alembic.ini`, scripts in `backend/migrations/versions/`. `docker-entrypoint.py` runs `alembic upgrade head` automatically (as `appuser`, after the data-dir chown) before exec'ing the app, so schema changes apply on every container start with no manual step — a failed migration aborts startup rather than serving the app against a stale schema. This works the same for a brand-new, empty database as for an existing one: the migration history is a single squashed revision that creates the schema from scratch (no pre-1.0 installs to preserve, so it gets re-squashed rather than accumulating dead history — see `docs/adr/`). Manual runs still work: `docker compose run --rm backend alembic upgrade head`. `main.py`'s startup lifespan also calls `Base.metadata.create_all()` independently of Alembic, which is what actually bootstraps the schema for local dev that never runs a migration.
- Tests: `backend/tests/`, run with pytest (`pytest.ini` sets `testpaths = tests`, `pythonpath = .`); prioritization strategy and per-tier status tracked in `ROADMAP.md`'s Testing section. Coverage (`pytest-cov`/`vitest --coverage`) uploads to Codecov from CI on every push — badge in `README.md`.
- CI (`.github/workflows/ci.yml`): besides backend/frontend tests and a docker-build smoke test, runs `pip-audit`/`yarn npm audit` (dependency CVEs) and Trivy (built-image CVEs) as report-only (`continue-on-error: true` — the dependency tree pulls in OSINT tools outside this repo's control, e.g. maigret/social-analyzer/mailcat-osint/pyppeteer, likely already carrying unfixable transitive findings), plus CodeQL (SAST, Python+JS) and gitleaks (secret scanning) as separate blocking jobs — free here since gitleaks-action's paid tier applies only to org-owned repos.
- `.github/workflows/release.yml` (tag push `v*.*.*`) builds multi-arch (`amd64`/`arm64`) backend/frontend images, pushes each by digest, then merges into one manifest list per image. Each published manifest-list digest gets a CycloneDX SBOM (`anchore/sbom-action`) and a Sigstore-signed build-provenance attestation (`actions/attest`), both pushed to GHCR alongside the image — verify either with `gh attestation verify oci://ghcr.io/<owner>/corvid-backend:<tag> --owner <owner>` (why post-merge rather than per-arch, see `docs/adr/`).
- `.github/dependabot.yml` opens weekly update PRs for `pip`, `npm-and-yarn`, `docker` (both Dockerfiles), and `github-actions`, each with a 3-day `cooldown` as a supply-chain mitigation (a malicious release published and yanked within days never reaches a PR).
- `.pre-commit-config.yaml` runs gitleaks locally pre-commit (same tool as CI's `secret-scan` job, catching a secret before it enters git history rather than after a push). Setup: `pip install pre-commit && pre-commit install`.
- `docker-compose.yaml`'s `backend` service has `env_file: {path: .env, required: false}` — a root-level `.env` (see `.env.example`) is NOT picked up by the container otherwise; compose's own automatic `.env` loading only covers variable substitution *within* the compose file, not the container's process environment.

## Frontend architecture

`frontend/src/features/` mirrors the backend feature split — one directory per module (`newsfeed`, `ioc-tools`, `email-analyzer`, `image-tools`, `llm-templates`, `cvss-calculator`, `rule-creator` (Sigma/Yara/Snort rule builder), `username-search`, `email-search`, `reddit-search`, `settings`). Each feature dir typically has its own `components/`, `hooks/`, `services/` (API calls), `constants/`, `utils/`. Entry: `src/App.jsx` → `src/index.jsx`. `src/core/` holds shared/cross-feature code.

i18n: `frontend/src/core/i18n/` (`en`/`ru`, one JSON per feature namespace). When batch-translating a feature via subagents, see `frontend/I18N_PATTERN.md` — don't duplicate the code pattern/rules/deliverable format in each subagent's prompt, point at that file instead (only pass scope/namespace/output per subagent). Default to English-only for new keys/features — add `ru` only when explicitly asked; existing `ru` coverage is otherwise incomplete on purpose right now.

New top-level features need edits in three places beyond their own directory: `src/core/config/routes.jsx` (lazy route), `src/core/config/sidebarConfig.jsx`'s `MAIN_MENU_ITEMS_CONFIG` (nav entry, including `aliases`/`tags`/`accepts` — the command palette's registry, `commandRegistry.js`, derives directly from this array, so a missing entry there is unreachable from search; `commandRegistry.test.js` fails on empty/garbage fields), plus a tabs config + `Layout.jsx`'s `currentTabs` path-match branch only if the feature has its own sub-tabs (rendered in the existing per-feature sidebar `Drawer`, unchanged, immediately right of the palette's own `LeftPanel`) — and a `website/` stub page (see Documentation site below), which lives outside `frontend/` entirely so `.github/scripts/check-docs-coverage.mjs` hard-fails CI (`ci.yml`'s `frontend` job) if a `MAIN_MENU_ITEMS_CONFIG` entry's `moduleId` has no matching `features/<slug>.md`.

**Command palette** (`/` or `⌘K`/`Ctrl+K` from anywhere, full spec in `docs/command-palette-plan.md`): `core/utils/commandParser.js` is a framework-free parser for the search grammar (`#tag`, `type:kind`, `>action`, `value tool` pivot, `defang`/`fang`, playbooks); `core/utils/iocTypeDetection.js` is a JS port of `ioc_utils.py`'s `determine_ioc_type()`, kept in sync via the shared fixture `testdata/ioc-type-detection-cases.json` (consumed by both `test_ioc_type_detection.py` and the JS test). `core/hooks/useCommandPalette.js` owns all palette state (open/close, recording, breadcrumbs) and is only instantiated once, in `CommandPalette.jsx` (mounted in `Layout.jsx`, inside the `AccessGate` subtree); other components open it by dispatching the `OPEN_COMMAND_PALETTE_EVENT` window event rather than lifting state. Playbooks (recorded tool-ID chains) and pinned/recent tools live in `localStorage` via `core/utils/commandPaletteStorage.js`. The `/` route renders `StartScreen.jsx` (a lighter, non-modal subset of the same grammar) unless Settings → Command Palette's `start_screen` is set to `newsfeed` — three new `GeneralSettings` columns (`auto_open_on_single_match`, `start_screen`, `always_tiles`) back that settings tab. `IOC_TYPES.YOUTUBE_VIDEO_URL` is deliberately excluded from `detectIocType`'s own priority chain (a YouTube link is still typed plain `URL` there, so `ioc_lookup`'s provider routing for it is unaffected) — `commandParser.js`'s `parseQuery` injects the `youtube` module's match itself via a separate `isYoutubeVideoUrl()` check, layered on top of the normal `URL` match rather than replacing it.

Cross-feature "send to X" actions (e.g. `email_search`'s found email → `ioc_lookup`, `ioc_lookup`'s domain result → `domain_finder`) pass the value via a `?q=` query param (`core/utils/crossFeatureNav.js`'s `buildPrefillUrl`); the target feature reads and clears it on mount via `core/hooks/usePrefillFromQuery.js`. `core/components/ui/ChainActionButton.jsx` is the reusable trigger. A palette pivot (`value tool`, e.g. `john_doe reddit`) uses the same mechanism — any single-value "identity" lookup wired for it (`reddit-search`, `username-search`, `email-search`, `git-recon`'s nickname mode) needs two things or the value silently never arrives despite a successful navigation: its root component's `index` → `"new"` redirect must be `<Navigate to={{ pathname: 'new', search: location.search }} replace />`, not a bare `to="new"` (which drops the query string), and the `"new"` tab must call `usePrefillFromQuery()` to both fill the form (`|| ''`, not a default param — the hook yields `null`, not `undefined`) and trigger the search itself. `{Reddit,Username,Email,GitRecon}Search.test.jsx` regression-test this pattern; a new identity-style feature should add its own copy.

## Documentation site

`website/` is the public docs site at `https://z0rats.github.io/corvid/` — the deep reference for
every feature, setting, and deployment concern; `README.md` stays a short pitch that links out to
it rather than duplicating detail. Separate from this repo's internal `docs/` (ADRs, plans, audits
— those stay repo-only). Built with **Astro + Starlight** (Vite-based, matches the frontend's
tooling), own `package.json`/`yarn.lock` (Yarn 4, `nodeLinker: node-modules`, not part of any
workspace). Content lives under `website/src/content/docs/` as Markdown/MDX, sectioned
`getting-started/`, `usage/`, `architecture/`, `features/` — `astro.config.mjs`'s sidebar is
`autogenerate` per section, so a page's frontmatter `sidebar: { order: N }` (gapped by 10; omit
it and the page just sorts to the end of its section, per Starlight's own fallback) is the only
place its nav position is declared. Ground new pages in the actual source (routers/schemas), not
recollection, and never link an external URL you haven't confirmed (verify via package metadata
rather than guessing a project's GitHub org). A new top-level feature just needs a stub page under
`features/` — `.github/scripts/check-docs-coverage.mjs` (see Frontend architecture above) gates the rest.
Deploys via `.github/workflows/docs.yml` on every push to `main` touching `website/**`.

## Browser extension

`extension/` is a minimal MV3 Chrome extension ("Quick Send") built around IOC-type detection
(`ioc-type-detection.js`, a hand-rolled port of `frontend`'s `iocTypeDetection.js`, shared by all
three surfaces below) gating three ways in to `<base_url>/ioc-tools/lookup?q=...` — the only
Corvid backend/token interaction anywhere in the extension:
- **Content script** (`content.js`, `matches: <all_urls>` — the one broad, install-time
  permission this extension asks for): a DeepL-style floating popup next to a text selection,
  shown only on an unambiguous type match; click messages the background script (content
  scripts can't call `chrome.tabs` directly).
- **Right-click menu** ("Corvid", one flat parent — no nested submenus, items scoped by click
  context): IOC lookup on a selection (title updated live via `chrome.contextMenus.onShown`),
  reverse image search (Google Lens/Yandex/Bing/TinEye, list hand-kept in sync with `frontend`'s
  `imageConstants.js`), and an EXIF metadata viewer (`exif-parser.js`, hand-rolled
  TIFF/EXIF/GPS parser covering JPEG/PNG/WebP/TIFF, shared via `importScripts()` in the service
  worker and a `<script>` tag in `sidepanel.html`; reading image bytes cross-origin needs a
  `http(s)://*/*` host permission requested at runtime on first use — narrower and opt-in,
  unlike the content script's install-time grant).
- **Side panel** (`sidepanel.html`/`.js`, opened on the current tab via
  `chrome.sidePanel.setPanelBehavior({openPanelOnActionClick: true})` when the toolbar icon is
  clicked — mutually exclusive with `chrome.action.onClicked`, so there's no listener for it):
  one document, two tabs — **Home** (search box, a few hand-picked quick links, and the base-URL
  setting — same `chrome.storage.local` key `options.html`/`options.js` still read/write as a
  fallback settings entry point) and **EXIF** (the viewer above), auto-switching to EXIF only
  when a right-click just triggered it (a `storage.session` write newer than 5s) so a plain
  toolbar-icon open always lands on Home.

No build step, load unpacked. Separate from `frontend/`, not part of any build/test pipeline.
See `extension/README.md` for setup (including where to look when the EXIF panel silently fails
— its own service-worker console, not the page's); `ROADMAP.md`'s "Chrome extension as a thin
client" entry has the fuller planned scope (token-based API calls) this MVP is a slice of.

## Conventions worth knowing

- Settings/config uses `pydantic-settings` with per-domain `BaseSettings` subclasses, each with its own `env_prefix` (e.g. `DB_`, `LOG_`, `API_`, `SCHEDULER_`), all loaded from a single `.env` (gitignored, not present in repo — none committed).
- `core/config/log_redaction.py`'s `SecretRedactionFilter` is attached to every logging handler (console + both file handlers, `logging_config.py`) and scrubs API-key-shaped substrings (query params, `Bearer` tokens, IPQualityScore's path-embedded key) out of every log record. Needed because several IOC-lookup providers (Hunter.io, Pulsedive, Shodan, Google Safe Browsing, IPQualityScore) pass their key in the request URL rather than a header, and `httpx.HTTPStatusError`'s `str()` embeds the full URL — a broad `except Exception: logger.error(..., str(e))` would otherwise leak it into `data/logs/*.log`. Matches by pattern (not by looking up live key values), so new providers are covered automatically.
- In route handlers, prefer injecting settings via dependency (`SettingsDep`) rather than importing the module-level `settings` singleton, so tests can override via `app.dependency_overrides`.
- Feature module layering pattern: `routers` (HTTP) → `service` (business logic) → `crud` (DB access) → `models`/`schemas`. New features should follow this same split.
- File-upload endpoints (`image_tools`, `email_analyzer`) share their read-validate-dispatch shape via `core/utils/file_upload.py`: `validate_uploaded_file(file, *, no_file_code, read_error_code, validate_fn)` reads and validates against a feature's own `validate_file_upload(filename, size) -> (is_valid, error_code, error_message)`, returning raw bytes or raising a 400 `AppHTTPException`; `run_file_endpoint(service_fn, *args, error_code, failure_message, value_error_code=None, run_in_thread=True)` dispatches the service call (via `asyncio.to_thread` unless `run_in_thread=False`, for an already-async `service_fn`) and maps `ValueError`/other exceptions to a 422. A new upload endpoint should use these rather than duplicating the try/except.
- Any external tool integrated behind a UI-facing feature (maigret, social-analyzer, mailcat-osint, gitcolombo, ...) must expose a way to see its currently-installed version and whether a newer one is available — these are pinned in `requirements.txt` at image-build time and can silently drift from upstream otherwise. Read the installed version via `importlib.metadata`; for the PyPI-latest-version half, use `core/utils/pypi_version_check.py`'s `check_for_update`/`compute_update_available` (shared by `username_search`'s maigret/social-analyzer settings and `email_search`'s `GET /api/email-search/info`) rather than a new per-tool fetch+persist block. A container rebuild is still required to actually install an update — this only flags that one's available.
- Scan-style features (SSE-streamed, cancellable/resumable, persisted run history - `username_search`'s three sources, `email_search`, `git_recon`) share their lifecycle via `core/scans/run.py`'s `ScanRun`: `execute()` creates the running row, emits a `started` `ScanEvent`, runs the feature's own `run_work(search_id)` coroutine (which emits its own `progress` events and returns a `ScanOutcome`), then marks the row completed/cancelled/failed and emits the matching terminal event - wire shape is the nested `{"type": ..., "data": {...}}`, adapted onto the raw `asyncio.Queue` `sse_response` reads from (queue → `StreamingResponse`) via `core/scans/sse.py`'s `queue_sink`. `ScanRun.cancel(feature_name, search_id)` looks up a process-local `Cancellable` (`core/scans/cancellable.py`'s `TaskCancellable`/`ProcessCancellable`/`GitCloneCancellable`, registered per scan under `(feature_name, search_id)` so two features' independently-incrementing search ids never collide) and awaits its `cancel()` - real cancellation, not just a signal. `core/scans/reconciliation.py`'s `mark_stale_running_as_failed` (stale-'running'-row cleanup on restart) rounds out the shared backend plumbing. Frontend `core/hooks/useResumableScan.js` mirrors this (stream buffering/parsing, backoff reconciliation after a dropped connection, abort lifecycle): each feature supplies its own `reduce`/`reconcile` event-to-state mapping (reading `event.type`/`event.data.*`) and an `api` object; `cancelScan` is exposed whenever `api.cancelScan` is provided - all three scan-style features (including git_recon) now support it. A new scan-style feature should use these rather than reimplementing the lifecycle.
- New models needing row-creation/last-write timestamps should mix in `core/models/mixins.py`'s `TimestampMixin` (`created_at`/`updated_at`) rather than declaring the columns by hand — existing tables use 6 different ad-hoc names for the same concept (`docs/database-schema-audit.md` section 3, finding #5). Domain-meaningful times (`started_at`/`completed_at`, `fetched_at`) are a different concept and keep their own names.
- AGPL-3.0 licensed (≤ v0.1.0 MIT) — mind this when adding dependencies or discussing licensing.
- Minimize new dependencies — prefer implementing small pieces of functionality ourselves over pulling in a library for it. Reach for a dependency only when the functionality is genuinely non-trivial (crypto, parsing, protocol handling) or already a de facto standard in this stack.
- Complexity budget: a file pushing ~1000 lines, or a function over ~150 lines / 8 parameters, is a signal to decompose — not a hard cap, but a prompt to split rather than keep growing it.
- New code touching shared/concurrent state (DB rows read-then-written across `await` points, in-memory caches, background tasks, SSE scan state, scheduler jobs) must be checked for race conditions — concurrent mutation, TOCTOU gaps, non-atomic read-modify-write — before merging.
- After fixing a bug, ask whether the same failure class could reach through a different surface; if so, prefer a structural test/gate that makes the whole class impossible over patching the one instance — this repo's existing examples are `tests/core/test_ssrf_guard_coverage.py` and `tests/features/git_recon/test_url_allowlist.py` below, each written after a specific gap, now catching every future instance of it.
- Any code that makes an HTTP request to a URL/host supplied (directly or indirectly) by the user must go through `core/security/ssrf_guard.py`'s `safe_get` — otherwise it's an SSRF vector into the docker network, localhost, or cloud metadata endpoints; `tests/core/test_ssrf_guard_coverage.py` fails on a new raw `httpx`/`requests` client that isn't on its reviewed fixed-host allowlist.
- Security headers are set in two independent places, since the backend's middleware never sees the SPA's own response: `core/config/security_config.py`'s `SecurityHeadersMiddleware` covers `/api/*`, `/docs`, `/redoc`, `/openapi.json` (CSP is relaxed to allow `cdn.jsdelivr.net` + inline init script specifically on `/docs`/`/redoc`, since Swagger/ReDoc need it and those routes are access-token gated with no user-supplied content anyway); `frontend/nginx.conf`'s `location /` sets the same base headers + a strict CSP for the actual HTML/JS the browser renders. HSTS stays production-only (`ENVIRONMENT=production`) since it must not be sent over plain HTTP, which is this app's default.
- `backend/requirements.txt` is a lock file compiled from `backend/requirements.in` via `uv pip compile requirements.in --override lxml-override.txt` — edit `.in` and regenerate with that command rather than hand-editing the lock. `maigret[pdf]` (not bare `maigret`) is the direct requirement, since its `pdf` extra is what actually provides `xhtml2pdf`/`svglib`/`pyhanko` etc. that `core/reports/` depends on for PDF rendering. `maigret` also declares `lxml>=6.0.2` while `newspaper4k` pins `lxml<6.0.0`; resolved via `lxml-override.txt` (`lxml==5.4.0`) since maigret doesn't import lxml directly — re-verify this override before bumping lxml (`social-analyzer`'s unpinned `lxml` dep and `mailcat-osint`'s `requests-html`→`pyppeteer` chain are both already compatible with it).

## Useful commands

- `make up` / `make rebuild` — start (or rebuild + start) full stack via Docker.
- `make up-backend` / `make rebuild-backend`, `make up-frontend` / `make rebuild-frontend` — per-service.
- `docker compose run --rm backend alembic upgrade head` — apply DB migrations.
- Backend tests: `cd backend && pytest`. Sync your venv first — `uv pip install -r requirements.txt --override lxml-override.txt` (same command CI's blocking test step uses) — since a stale/partial local venv can pass locally while silently missing an import error that CI's full install would catch (or vice versa).
- Frontend dev: `cd frontend && yarn start` (uses `--openssl-legacy-provider`); build: `yarn build`; test: `yarn test`.
- Docs site dev: `cd website && yarn dev`; build: `yarn build` (output `website/dist/`).
- App served at `http://localhost:4000` once containers are up.
