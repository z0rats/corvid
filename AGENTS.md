# Corvid — project context

Self-hostable, single-user OSINT/security-analyst web app. FastAPI backend + React frontend, runs via Docker Compose. Not production-hardened (early prototype, per README).

**Maintenance:** this file loads in full on every message regardless of task, so its size is a standing tax on every conversation — treat growth as a cost, not a free action.

- Update it after any important project change (new feature, new external dependency, architectural shift) — but each edit is a *net* pass: prune or tighten something (merge, generalize, cut what's now covered elsewhere or obvious from the code) roughly as much as you add. Don't just append.
- Record big architectural decisions (new dependency choice, schema/storage tradeoffs, anything picking one approach over a real alternative) as a new `docs/adr/NNNN-*.md` — don't let the reasoning live only in chat/commit history. Keep entries in this file itself pointer-short; the ADR holds the "why".
- For a feature/subsystem whose implementation detail (exact mechanisms, gotchas, edge cases) has grown past a couple of sentences, move that detail into `docs/architecture/<slug>.md` (not loaded every turn, so no size pressure there) and leave a 2-4 sentence summary + `Deep-dive: docs/architecture/<slug>.md` pointer here. This file should stay a map to where deeper info lives, not the deep info itself.
- Describe the **current state only**. No "was X, changed to Y because Z", no "see commit/PR #123", no incident narratives, no migration history — that belongs in commit messages and git history, which are queryable on demand and don't cost tokens on every turn. If a past decision needs to stay discoverable, a short present-tense reason clause (e.g. "X, since Y" ) is fine; a paragraph of backstory is not.
- No speculative or redundant detail.
- If this file is pushing 35KB+, that's a signal to condense before adding more — collapse verbose bullets, drop detail that's redundant with the code itself, and prefer pointing at a file/symbol or a `docs/architecture/<slug>.md` deep-dive over re-explaining what it does.
- Also periodically update `README.md` with important user-facing changes — especially anything affecting deployment (new required setup step, changed env vars, new `.env`/`docker-compose.yaml` behavior) — since that's what operators actually read when installing/upgrading.

## Git

Never run `git commit` (or `git push`) yourself, create new tags or releases, regardless of how the rest of the task is scoped or how routine the change looks. Stage or leave changes uncommitted and let the user review and commit. This holds even if a broader instruction ("go ahead and update the repo", "ship this") could be read as covering it.

## Stack

- **Backend**: Python 3.14, FastAPI, SQLAlchemy 2.0 (async, `aiosqlite`/`asyncpg`), Alembic migrations, APScheduler for background jobs, `pydantic-ai-slim[anthropic,google,openai]` for LLM features (the bare `pydantic-ai` metapackage is deliberately not installed — it hard-depends on every provider SDK; `app/utils/llm_service.py`'s model registry also auto-discovers models pulled into a local Ollama server via its OpenAI-compatible `/v1/models` endpoint - `LLM_OLLAMA_BASE_URL`, no API key needed, silently skipped if unreachable), `slowapi` for rate limiting, pytest for tests.
- **Frontend**: React 19, MUI 9, Jotai (state), react-router 8 (declarative mode only - `BrowserRouter`/`Route`/hooks imported from `react-router`, not the removed `react-router-dom` package), Vite (build/dev server) + Vitest (tests, jsdom), ESLint 10 flat config (`frontend/eslint.config.mjs`), Yarn 4 (berry, `packageManager: yarn@4.15.0`). TypeScript is being adopted incrementally (`allowJs`, convert-on-touch, no bulk rewrite) — see `docs/frontend-typescript-migration-plan.md`; `typescript` is pinned below latest (`~6.0.3`) since `7.x`'s package-layout change breaks Yarn 4.15's builtin compat patch and isn't yet in `typescript-eslint`'s peer range.
- **DB**: SQLite by default at `data/corvid.db` (see `backend/app/core/config/settings.py` — `DatabaseSettings`, env prefix `DB_`). Logs at `data/logs/`.
- **Deploy**: `docker-compose.yaml` — `backend` (no exposed port, mounts `./data`) + `frontend` (nginx, port 4000). `make up` / `make rebuild` / `make up-backend` / `make up-frontend` (see `Makefile`). Backend runs as non-root `appuser` (UID/GID 1000): `backend/docker-entrypoint.py` starts as root just long enough to `chown` the host-owned bind-mounted `./data`, then drops to `appuser` via `setuid`/`setgid`, runs migrations (see below), and `execvp`s into the real `uvicorn` command. `appuser`'s home directory (build-time, not bind-mounted) is where maigret's site-database (`~/.maigret`) and pyppeteer's lazily-downloaded Chromium (`~/.local/share/pyppeteer`, only if `email_search`'s headless checks are enabled) end up.

## Backend architecture

Entry point: `backend/main.py` — builds the FastAPI app via `create_fastapi_application()`, lifespan hooks create DB tables, run app defaults, start background favicon fetch, start scheduler.

Layout under `backend/app/`:
- `core/` — cross-cutting concerns (`config/`, `settings/`, `security/ssrf_guard.py`, `reports/`, `alerts/`, `database.py`, `scheduler.py`, `dependencies.py`, `exceptions.py`, `healthcheck.py`). Deep-dive: `docs/architecture/core-cross-cutting.md`. Highlights: `api_keys.Apikey.key` is encrypted at rest (Fernet, `secrets_crypto.py`); `ssrf_guard.py`'s `safe_get` is the single required entrypoint for any server-side fetch of a user-supplied URL (pins the resolved IP, re-validates every redirect hop); `reports/` is the shared HTML/PDF renderer used by `ioc_lookup`, `email_analyzer`, and `ru_business_check`.
- `features/` — one directory per product feature, each typically split into `routers/`, `service/`, `schemas/`, `models/`, `crud/`, `utils/`, `config/`:
  - `newsfeed/` — RSS aggregation, IOC extraction from articles, MITRE ATT&CK mapping, trends/analytics. Each `NewsfeedSettings` row tracks `last_fetched_at`/`last_success_at`/`last_error`, updated per-feed by `feed_processing_service.py`'s `process_feed_chunk` on every scheduler run, so a persistently failing feed (bad URL, provider outage) shows a warning in the feed management UI instead of only ever appearing in logs.
  - `ioc_tools/` — `ioc_lookup` (single + bulk IOC lookups against AbuseIPDB, AlienVault, VirusTotal, Shodan, etc., plus a keyless local `blacklist` provider for EVM/Bitcoin addresses), `ioc_extractor`, `ioc_defanger`, `domain_finder` (URLScan.io typosquat/phishing discovery + keyless WHOIS/RDAP/DNS/crt.sh panels, plus an optional-key DNSDumpster panel). Deep-dive: `docs/architecture/ioc-tools.md`.
  - `email_analyzer/` — `.eml` parsing, header/IOC checks, AI-assisted analysis.
  - `image_tools/` — EXIF/metadata extraction, hashing, reverse image search deep-links (no API key needed), plus an optional AI photo-geolocation hypothesis (`POST /api/image/geolocate`, `image_geolocation_service.py`) reusing `llm_service.py`'s multimodal support (`execute_structured_prompt`'s `image_data`/`image_media_type`) — the module's only feature needing an LLM key or an `ai_settings.image_geolocation_model` override; still fully stateless like the rest of the feature (no history persisted). See `docs/geoint-photo-analysis-plan.md` for the fuller backlog this MVP slice came from.
  - `llm_templates/` — user-defined AI prompt templates (categories + templates).
  - `cvss_calculator/` — CVSS 3.1/4.0 scoring.
  - `username_search/` — two pluggable sources behind one unified schema (`source`: `maigret` | `social_analyzer`), selected per-scan via `ScanRequest.source` (`POST /api/username-search/scan`): **maigret** runs in-process with true per-site SSE progress; **social-analyzer** runs as a subprocess of its installed CLI (its package can't be imported), so progress is coarse and it's bounded by a `PROCESS_WATCHDOG_SECONDS` wall-clock ceiling. Both expose a PyPI-latest-version check but need a container rebuild to actually update. Report export only works for maigret-sourced runs. A keyless Hudson Rock supplementary check (`GET /api/username-search/hudson-rock`) adds an infostealer-exposure status chip. Deep-dive: `docs/architecture/username-search.md`.
  - `email_search/` — finds which mail providers a username is registered at, via `mailcat-osint`'s ~26 per-provider checker coroutines (SMTP probing, provider APIs, headless Chromium), driven in-process and bounded by an `asyncio.Semaphore`, progress over SSE. SMTP and headless-Chromium checker groups are both gated off by default (need outbound TCP/25 or lazily download Chromium, respectively). A psutil-based reaper cleans up orphaned Chromium processes after a per-checker timeout. Deep-dive: `docs/architecture/email-search.md`.
  - `reddit_search/` — finds a Reddit user's full post/comment history, including moderator-removed and author-deleted content, by querying Arctic Shift and PullPush archive APIs in parallel (no auth/API key; server-side port of the frontend-only [Rosint](https://github.com/zuxu4n/Rosint)). `service/reddit_search_service.py` merges+dedupes by Reddit item ID, sorted desc by `created_utc`; pagination is timestamp-cursor-based (`before`/`after`), not offset-based. One `RedditSearch` row persists per username investigation (`POST /api/reddit-search/scan`), pages appended idempotently to `RedditSearchResult` (unique on `search_id`+`kind`+`reddit_id`) so paging back doesn't duplicate rows. No settings module.
  - `dork_runner/` — runs a static library of parameterized dork templates (`site:`, `filetype:`, `intext:`, etc., `config/dork_templates.py`) against a domain/username/email, ephemeral like `domain_finder` (no persistence/history). DuckDuckGo's HTML endpoint is the default engine since Google/Bing block scripted queries almost immediately; Google/Bing are still selectable but best-effort. Queries run sequentially with a politeness delay between them (`config/search_engines_config.py`), never in parallel. `POST /api/dork-runner/run`, `GET /api/dork-runner/templates`.
  - `youtube/` — metadata lookup for a YouTube video URL (`POST /api/youtube/lookup`), ephemeral like `domain_finder`/`dork_runner` (no persistence). Keyless tier: oEmbed (title/author/thumbnail/embed html) plus a best-effort scrape of the page's Open Graph/schema.org `<meta>` tags (`youtube_page_service.py`) for description/duration/publish-date/keywords, plus directly-constructed `i.ytimg.com` thumbnail URLs at every resolution (may 404 for `maxresdefault`). An optional YouTube Data API v3 key (`core/settings/api_keys`, service key `youtube`) unlocks view/like/comment counts, tags, category — same optional-key pattern as DNSDumpster, but mandatory for `POST /api/youtube/comments` (no keyless tier there): with no `query`, a plain paginated listing; with a `query`, server-side multi-page filtering by author/text (the Data API has no native comment-text search), capped on pages/results (`youtube_config.py`), returning `truncated: true` + `next_page_token` if the cap hit first. `youtube_url_utils.extract_video_id` handles `youtu.be`/`watch`/`shorts`/`embed`/`live` URL shapes.
  - `git_recon/` — wraps [gitcolombo](https://github.com/Soxoj/gitcolombo) in-process to correlate names/emails/GitHub logins from commit history. Three modes: `search` (API-only, no cloning) and `url`/`nickname` (clone repos, correlate author/committer identity mismatches). SSE-streamed, cancellable, same lifecycle pattern as `username_search`/`email_search`. `git clone` is a `subprocess` call outside `ssrf_guard`'s reach — gated instead by its own GitHub-URL allowlist (`validate_github_repo_url`). Reuses the `github_pat` API key. Deep-dive: `docs/architecture/git-recon.md`.
  - `ru_business_check/` — Russian-market due-diligence check by ИНН/company name, orchestrated via the shared SSE-scan pattern (`POST /api/ru-business-check/scan`) across 7 sources: ЕГРЮЛ, disqualified-persons (РДЛ), arbitration history, Федресурс bankruptcy, Прозрачный бизнес, ФедСФМ, and zakupki.gov.ru's РНП — feeding one risk engine (`flag_engine.py`). Only ИНН-precise sources (Федресурс, РНП) produce hard flags; name-matched sources (РДЛ, ФедСФМ) are always soft, to avoid same-name false positives. Repeat lookups within 24h are cached; exportable as HTML/PDF. UI/report text is Russian-only by design. Deep-dive (per-source detail, TLS/CAPTCHA handling, sources ruled out): `docs/architecture/ru-business-check.md`.
- **Access control**: no user accounts (single-user tool) — `core/security/access_control.py` guards every `/api/*` route (plus `/docs`/`/redoc`/`/openapi.json`) behind one shared bearer token (`verify_access_token`, wired as a router-level dependency in `router_registry.py`). Token comes from `API_ACCESS_TOKEN` or is auto-generated and persisted to `<data_dir>/.access_token` (0600), printed once at startup — same pattern as the encryption key, shared via `core/security/persisted_secret.py`. `healthcheck.router` and the alerts `ws_router` are the only unguarded routers: healthcheck has no sensitive data, and the WS handshake checks the same token via a `?token=` query param (browsers can't set a custom header on a WS handshake). Frontend: `baseApi.js` attaches the token from `localStorage` to every request and reloads on a 401; `AccessGate.jsx` shows a one-time entry screen when no token is stored.
- All routers are aggregated in `backend/app/utils/router_registry.py` via `get_core_routers()`, `get_settings_routers()`, `get_feature_routers()`, then mounted in `main.py`.
- Migrations: Alembic, config at `backend/alembic.ini`, scripts in `backend/migrations/versions/`. `docker-entrypoint.py` runs `alembic upgrade head` automatically (as `appuser`, after the data-dir chown) before exec'ing the app — a failed migration aborts startup rather than serving a stale schema. Migration history is a single squashed revision that creates the schema from scratch (no pre-1.0 installs to preserve — see `docs/adr/0001-squash-migration-history.md`). Manual run: `docker compose run --rm backend alembic upgrade head`. `main.py`'s startup lifespan also calls `Base.metadata.create_all()` independently, which is what bootstraps local dev that never runs a migration.
- Tests: `backend/tests/`, run with pytest (`pytest.ini` sets `testpaths = tests`, `pythonpath = .`); prioritization strategy and per-tier status tracked in `ROADMAP.md`'s Testing section. Coverage (`pytest-cov`/`vitest --coverage`) uploads to Codecov from CI on every push — badge in `README.md`.
- CI (`.github/workflows/ci.yml`): backend/frontend tests, a docker-build smoke test, `pip-audit`/`yarn npm audit` (dependency CVEs), and Trivy (built-image CVEs) run alongside backend `ruff check`/`ruff format --check`/`mypy app` as report-only (`continue-on-error: true` — scanners because the OSINT-tool dependency tree, maigret/social-analyzer/mailcat-osint/pyppeteer, likely carries unfixable transitive findings; lint/type-check because of a pre-existing backlog predating the tooling, to be flipped to blocking once triaged down). CodeQL and gitleaks are separate blocking jobs. The frontend job's `eslint`/`tsc --noEmit` are blocking, unlike the backend's, since the TypeScript migration (`docs/frontend-typescript-migration-plan.md`) started clean.
- `.github/workflows/release.yml` (tag push `v*.*.*`) builds multi-arch (`amd64`/`arm64`) backend/frontend images, pushes each by digest, then merges into one manifest list per image. Each published manifest-list digest gets a CycloneDX SBOM (`anchore/sbom-action`) and a Sigstore-signed build-provenance attestation (`actions/attest`), both pushed to GHCR alongside the image — verify either with `gh attestation verify oci://ghcr.io/<owner>/corvid-backend:<tag> --owner <owner>` (why post-merge rather than per-arch, see `docs/adr/0005-sbom-attestation-on-merged-manifest.md`).
- `.github/dependabot.yml` opens weekly update PRs for `pip`, `npm-and-yarn`, `docker` (both Dockerfiles), and `github-actions`, each with a 3-day `cooldown` as a supply-chain mitigation (a malicious release published and yanked within days never reaches a PR).
- `.pre-commit-config.yaml` runs gitleaks locally pre-commit (same tool as CI's `secret-scan` job, catching a secret before it enters git history rather than after a push), `ruff check --fix`/`ruff format` on staged `backend/` files, plus a local hook that regenerates `docs/database-schema.md` from the models whenever a `backend/app/**/models/*.py` file is staged (mirrors CI's staleness check — a diff fails the hook, `git add` the regenerated file and re-commit). mypy stays CI-only (not run pre-commit — not guaranteed fast enough). Setup: `pip install pre-commit && pre-commit install`.
- `docker-compose.yaml`'s `backend` service has `env_file: {path: .env, required: false}` — a root-level `.env` (see `.env.example`) is NOT picked up by the container otherwise; compose's own automatic `.env` loading only covers variable substitution *within* the compose file, not the container's process environment.

## Frontend architecture

`frontend/src/features/` mirrors the backend feature split — one directory per module (`newsfeed`, `ioc-tools`, `email-analyzer`, `image-tools`, `llm-templates`, `cvss-calculator`, `rule-creator` (Sigma/Yara/Snort rule builder), `username-search`, `email-search`, `reddit-search`, `settings`). Each feature dir typically has its own `components/`, `hooks/`, `services/` (API calls), `constants/`, `utils/`. Entry: `src/App.jsx` → `src/index.jsx`. `src/core/` holds shared/cross-feature code.

i18n: `frontend/src/core/i18n/` (`en`/`ru`, one JSON per feature namespace). When batch-translating a feature via subagents, see `frontend/I18N_PATTERN.md` — don't duplicate the code pattern/rules/deliverable format in each subagent's prompt, point at that file instead (only pass scope/namespace/output per subagent). Default to English-only for new keys/features — add `ru` only when explicitly asked; existing `ru` coverage is otherwise incomplete on purpose right now.

New top-level features need edits in three places beyond their own directory: `src/core/config/routes.jsx` (lazy route); `sidebarConfig.jsx`'s `MAIN_MENU_ITEMS_CONFIG` (nav entry, including `aliases`/`tags`/`accepts` — the command palette's `commandRegistry.js` derives directly from this array, so a missing entry is unreachable from search); and a `website/` stub page (see Documentation site below) — `.github/scripts/check-docs-coverage.mjs` hard-fails CI if a `MAIN_MENU_ITEMS_CONFIG` entry's `moduleId` has no matching `features/<slug>.md`. A feature with its own sub-tabs also needs a tabs config + `Layout.jsx`'s `currentTabs` path-match branch.

**Command palette** (`/` or `⌘K`/`Ctrl+K` from anywhere, UX spec in `docs/command-palette-plan.md`): framework-free grammar parser (`core/utils/commandParser.js`) plus a JS port of the backend's IOC-type detection kept in sync via a shared test fixture. Cross-feature "send to X" actions and the palette's `value tool` pivot both prefill a target feature via a `?q=` query param — any new single-value "identity" feature needs to wire this correctly or the pivot silently drops the value (see the deep-dive for the exact gotcha and its regression tests). Deep-dive: `docs/architecture/command-palette.md`.

## Documentation site

`website/` is the public docs site at `https://z0rats.github.io/corvid/` — the deep reference for
every feature, setting, and deployment concern; `README.md` stays a short pitch that links out to
it rather than duplicating detail. Separate from this repo's internal `docs/` (ADRs, plans, audits
— those stay repo-only). Built with **Astro + Starlight** (Vite-based, matches the frontend's
tooling), own `package.json`/`yarn.lock` (Yarn 4, `nodeLinker: node-modules`, not part of any
workspace). Content lives under `website/src/content/docs/` as Markdown/MDX, sectioned
`getting-started/`, `usage/`, `architecture/`, `features/` — `astro.config.mjs`'s sidebar is
`autogenerate` per section, so a page's frontmatter `sidebar: { order: N }` (gapped by 10; omit
it and the page just sorts to the end of its section, per Starlight's own fallback) is the only
place its nav position is declared. Ground new pages in the actual source (routers/schemas), not
recollection, and never link an external URL you haven't confirmed (verify via package metadata
rather than guessing a project's GitHub org). A new top-level feature just needs a stub page under
`features/` — `.github/scripts/check-docs-coverage.mjs` (see Frontend architecture above) gates the rest.
Deploys via `.github/workflows/docs.yml` on every push to `main` touching `website/**`.

## Browser extension

`extension/` is a minimal MV3 Chrome extension ("Quick Send") built around IOC-type detection
(`ioc-type-detection.js`, a hand-rolled port of `frontend`'s `iocTypeDetection.js`, shared by all
three surfaces below) gating three ways in to `<base_url>/ioc-tools/lookup?q=...` — the only
Corvid backend/token interaction anywhere in the extension:
- **Content script** (`content.js`, `matches: <all_urls>` — the one broad, install-time
  permission this extension asks for): a DeepL-style floating popup next to a text selection,
  shown only on an unambiguous type match; click messages the background script (content
  scripts can't call `chrome.tabs` directly).
- **Right-click menu** ("Corvid", one flat parent — no nested submenus, items scoped by click
  context): IOC lookup on a selection (title updated live via `chrome.contextMenus.onShown`),
  reverse image search (Google Lens/Yandex/Bing/TinEye, list hand-kept in sync with `frontend`'s
  `imageConstants.js`), and an EXIF metadata viewer (`exif-parser.js`, hand-rolled
  TIFF/EXIF/GPS parser covering JPEG/PNG/WebP/TIFF, shared via `importScripts()` in the service
  worker and a `<script>` tag in `sidepanel.html`; reading image bytes cross-origin needs a
  `http(s)://*/*` host permission requested at runtime on first use — narrower and opt-in,
  unlike the content script's install-time grant).
- **Side panel** (`sidepanel.html`/`.js`, opened on the current tab via
  `chrome.sidePanel.setPanelBehavior({openPanelOnActionClick: true})` when the toolbar icon is
  clicked — mutually exclusive with `chrome.action.onClicked`, so there's no listener for it):
  one document, two tabs — **Home** (search box, a few hand-picked quick links, and the base-URL
  setting — same `chrome.storage.local` key `options.html`/`options.js` still read/write as a
  fallback settings entry point) and **EXIF** (the viewer above), auto-switching to EXIF only
  when a right-click just triggered it (a `storage.session` write newer than 5s) so a plain
  toolbar-icon open always lands on Home.

No build step, load unpacked. Separate from `frontend/`, not part of any build/test pipeline.
See `extension/README.md` for setup (including where to look when the EXIF panel silently fails
— its own service-worker console, not the page's); `ROADMAP.md`'s "Chrome extension as a thin
client" entry has the fuller planned scope (token-based API calls) this MVP is a slice of.

## Conventions worth knowing

- Settings/config uses `pydantic-settings` with per-domain `BaseSettings` subclasses, each with its own `env_prefix` (e.g. `DB_`, `LOG_`, `API_`, `SCHEDULER_`), all loaded from a single `.env` (gitignored, not present in repo — none committed).
- A recurring `add_recurring_job` scheduler job's `IntervalTrigger` countdown lives only in-memory and resets on every process restart (no persistent job store) — on a host that restarts more often than the interval, the job can silently never fire. Any job whose data would otherwise go stale needs a startup-time catch-up check that re-derives staleness from the DB itself (e.g. `blacklist_refresh_service.is_blacklist_stale`, checked in `main.py`'s `_populate_blacklist_if_stale_in_background`), not just an empty-table check.
- `core/config/log_redaction.py`'s `SecretRedactionFilter` is attached to every logging handler (console + both file handlers, `logging_config.py`) and scrubs API-key-shaped substrings (query params, `Bearer` tokens, IPQualityScore's path-embedded key) out of every log record. Needed because several IOC-lookup providers (Hunter.io, Pulsedive, Shodan, Google Safe Browsing, IPQualityScore) pass their key in the request URL rather than a header, and `httpx.HTTPStatusError`'s `str()` embeds the full URL — a broad `except Exception: logger.error(..., str(e))` would otherwise leak it into `data/logs/*.log`. Matches by pattern (not by looking up live key values), so new providers are covered automatically.
- In route handlers, prefer injecting settings via dependency (`SettingsDep`) rather than importing the module-level `settings` singleton, so tests can override via `app.dependency_overrides`.
- Feature module layering pattern: `routers` (HTTP) → `service` (business logic) → `crud` (DB access) → `models`/`schemas`. New features should follow this same split.
- File-upload endpoints (`image_tools`, `email_analyzer`) share their read-validate-dispatch shape via `core/utils/file_upload.py`: `validate_uploaded_file(file, *, no_file_code, read_error_code, validate_fn)` reads and validates against a feature's own `validate_file_upload(filename, size) -> (is_valid, error_code, error_message)`, returning raw bytes or raising a 400 `AppHTTPException`; `run_file_endpoint(service_fn, *args, error_code, failure_message, value_error_code=None, run_in_thread=True)` dispatches the service call (via `asyncio.to_thread` unless `run_in_thread=False`, for an already-async `service_fn`) and maps `ValueError`/other exceptions to a 422. A new upload endpoint should use these rather than duplicating the try/except.
- Any external tool integrated behind a UI-facing feature (maigret, social-analyzer, mailcat-osint, gitcolombo, ...) must expose its currently-installed version and whether a newer one is available — these are pinned in `requirements.txt` at image-build time and can silently drift otherwise. Read the installed version via `importlib.metadata`; for the PyPI-latest-version half, use `core/utils/pypi_version_check.py`'s `check_for_update`/`compute_update_available` rather than a new per-tool fetch+persist block. A container rebuild is still required to actually install an update — this only flags that one's available.
- Scan-style features (SSE-streamed, cancellable/resumable, persisted run history — `username_search`'s three sources, `email_search`, `git_recon`, `ru_business_check`) share their lifecycle via `core/scans/run.py`'s `ScanRun` (backend) and `core/hooks/useResumableScan.js` (frontend) — a new scan-style feature should use these rather than reimplementing the lifecycle. Deep-dive: `docs/architecture/scan-lifecycle.md`.
- New models needing row-creation/last-write timestamps should mix in `core/models/mixins.py`'s `TimestampMixin` (`created_at`/`updated_at`) rather than declaring the columns by hand — existing tables use 6 different ad-hoc names for the same concept (`docs/database-schema-audit.md` section 3, finding #5). Domain-meaningful times (`started_at`/`completed_at`, `fetched_at`) are a different concept and keep their own names.
- AGPL-3.0 licensed (≤ v0.1.0 MIT) — mind this when adding dependencies or discussing licensing.
- Minimize new dependencies — prefer implementing small pieces of functionality ourselves over pulling in a library for it. Reach for a dependency only when the functionality is genuinely non-trivial (crypto, parsing, protocol handling) or already a de facto standard in this stack.
- Complexity budget: a file pushing ~1000 lines, or a function over ~150 lines / 8 parameters, is a signal to decompose — not a hard cap, but a prompt to split rather than keep growing it.
- New code touching shared/concurrent state (DB rows read-then-written across `await` points, in-memory caches, background tasks, SSE scan state, scheduler jobs) must be checked for race conditions — concurrent mutation, TOCTOU gaps, non-atomic read-modify-write — before merging.
- After fixing a bug, ask whether the same failure class could reach through a different surface; if so, prefer a structural test/gate that makes the whole class impossible over patching the one instance — this repo's existing examples are `tests/core/test_ssrf_guard_coverage.py` and `tests/features/git_recon/test_url_allowlist.py` below, each written after a specific gap, now catching every future instance of it.
- A new `ioc_lookup` provider needs `website/src/content/docs/features/ioc-tools.md` updated in the same change — a pre-commit hook (`scripts/check_new_ioc_provider_docs.py`) blocks a commit that grows `service_registry.py`'s provider count without it.
- Any code that makes an HTTP request to a URL/host supplied (directly or indirectly) by the user must go through `core/security/ssrf_guard.py`'s `safe_get` — otherwise it's an SSRF vector into the docker network, localhost, or cloud metadata endpoints; `tests/core/test_ssrf_guard_coverage.py` fails on a new raw `httpx`/`requests` client that isn't on its reviewed fixed-host allowlist.
- Security headers are set in two independent places, since the backend's middleware never sees the SPA's own response: `core/config/security_config.py`'s `SecurityHeadersMiddleware` covers `/api/*`, `/docs`, `/redoc`, `/openapi.json` (CSP relaxed for `cdn.jsdelivr.net` + inline init script on `/docs`/`/redoc` only, since those are access-token gated with no user-supplied content); `frontend/nginx.conf`'s `location /` sets the same base headers + a strict CSP for the SPA. HSTS stays production-only (`ENVIRONMENT=production`), since it must not be sent over plain HTTP, this app's default.
- `backend/requirements.txt` is a lock file compiled from `backend/requirements.in` via `uv pip compile requirements.in --override lxml-override.txt` — edit `.in` and regenerate with that command rather than hand-editing the lock. `maigret[pdf]` (not bare `maigret`) is the direct requirement, since its `pdf` extra is what actually provides `xhtml2pdf`/`svglib`/`pyhanko` etc. that `core/reports/` depends on for PDF rendering. `maigret` also declares `lxml>=6.0.2` while `newspaper4k` pins `lxml<6.0.0`; resolved via `lxml-override.txt` (`lxml==5.4.0`) since maigret doesn't import lxml directly — re-verify this override before bumping lxml (`social-analyzer`'s unpinned `lxml` dep and `mailcat-osint`'s `requests-html`→`pyppeteer` chain are both already compatible with it).

## Useful commands

`make help` lists all targets (Docker lifecycle, `test`/`test-backend`/`test-frontend`, `lint`/`lint-backend`/`lint-frontend`, `migrate`, `sync-backend`) with the exact invocations CI uses — prefer these over hand-typing `pytest`/`yarn`/`ruff`/`mypy` flags. Notes beyond what `make help` shows:

- `make lint-backend` runs `ruff check`/`ruff format --check`/`mypy app` (config: `backend/pyproject.toml`) and needs the synced venv below; it currently fails on the pre-existing backlog mentioned above under CI — that's expected until it's triaged down, CI doesn't block on it yet either.
- `make test-backend`/`lint-backend` need a synced local venv first — run `make sync-backend` (a stale/partial venv can pass locally while missing an import error CI's full install would catch, or vice versa).
- Frontend dev server (no Docker target for this): `cd frontend && yarn start` (uses `--openssl-legacy-provider`).
- Docs site dev: `cd website && yarn dev`; build: `yarn build` (output `website/dist/`).
- App served at `http://localhost:4000` once containers are up.
