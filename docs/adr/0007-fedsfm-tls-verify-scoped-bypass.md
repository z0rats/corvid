# RU government-site clients scope `verify=False` to themselves, don't trust the Russian root CA system-wide

`fedsfm.ru` (Росфинмониторинг's terrorism/WMD-financing list) and `zakupki.gov.ru` (Реестр недобросовестных поставщиков) — `ru_business_check`'s ФедСФМ and РНП sources — both serve a TLS certificate chained to the Russian national root CA ("Russian Trusted Root CA" / "Russian Trusted Sub CA", issued by the Ministry of Digital Development, ГУЦ Минцифры) — confirmed live via a direct handshake on each host (`SSL certificate problem: unable to get local issuer certificate`). That CA isn't present in any standard OS/container trust store, so a normal `httpx.AsyncClient()` call to either host fails outright.

Two ways to make the request succeed were considered: bundling the Russian root CA into the backend container's trust store (`update-ca-certificates`-style, Dockerfile-level), or scoping `verify=False` to only each source's own client. The container-wide-trust option was rejected: it would extend TLS trust for *every* outbound HTTPS connection this backend ever makes (favicon fetches, newsfeed article fetching, any user-supplied URL passed through `ssrf_guard`, every other IOC-lookup provider) to a foreign national CA whose issuance policy and revocation practices this project has no visibility into — a blast-radius mismatch for a need that's specific to a handful of fixed, already-scraped government hosts. It would also need periodic re-verification that the bundled cert file still matches the CA's actual current chain, an ongoing maintenance cost that would only grow as more `.gov.ru`-adjacent sources get added.

`verify=False` is applied only inside `fedsfm_service.py`'s and `zakupki_rnp_service.py`'s own `httpx.AsyncClient(...)` constructions — no other client in the codebase is affected, and each file's own docstring explains why (and points back here). The tradeoff accepted is the standard one for disabling TLS verification (no protection against a MITM'd response on that one connection), scoped as narrowly as possible and limited to fixed, publicly-keyless government APIs — the same "official sources only, CAPTCHA/anti-bot is a hard stop" posture as the rest of `ru_business_check`'s sources (see `docs/adr/0006-*.md`), just for a TLS-trust gap instead of an anti-bot block. Any future RU government source hitting the same CA chain should follow this same pattern rather than reopening the question.
