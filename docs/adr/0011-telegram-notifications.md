# Telegram notifications reuse the existing `Alert` model as the event bus

Corvid already had an `Alert` model + WebSocket broadcast (`core/alerts/`) meant to be a generic "something happened" event log, but nothing in the backend actually populated it — only a bare REST endpoint existed. Rather than inventing a second, parallel "notification event" concept for Telegram, `core/alerts/service/alerts_service.py`'s `raise_alert()` is now the one place an event gets recorded (DB row + WS broadcast), with Telegram delivery as an additional side effect of the same call. Anything that wants to notify — today or in the future — just calls `raise_alert()`; it doesn't need to know Telegram exists.

The two priority sources (scan completion/failure, recurring scheduler job failure) are wired in at their single existing shared choke points rather than at each of the 7 individual call sites: `core/scans/run.py`'s `ScanRun.execute()` already funnels every scan-style feature's terminal state through one method, and `core/scheduler.py`'s `wrap_job_errors()` already funnels every recurring job's failure through one wrapper. This means every current *and future* scan-style feature or recurring job gets notifications for free, with zero new plumbing per feature.

No bot-framework dependency (`python-telegram-bot`/`aiogram`) was added. v1 only needs one-way `sendMessage` — a single `httpx` POST to a fixed host (`api.telegram.org`), the same shape as any other keyless external API client already in this codebase, using the `httpx` dependency already present. Pulling in a bot framework would mean an update-loop/webhook lifecycle, a dependency with its own transitive surface, and features (inbound commands, conversation state) not needed yet. Inbound bot commands are deliberately out of scope for this iteration — they would need webhook or polling infrastructure the default single-container deployment doesn't have, and are left as a distinct future decision.

Recurring-job failure notifications are edge-triggered (in-memory per-job "currently failing" flag in `wrap_job_errors`), not fired on every failed tick — a job stuck failing for days would otherwise spam one message per scheduler interval indefinitely. Only the healthy→failing and failing→healthy transitions notify. This state is process-local and resets on restart (the same tradeoff `ScanRun`'s own cancellation registry already accepts), so the worst case after a restart is one duplicate notification, not silence.
